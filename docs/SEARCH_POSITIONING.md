# 検索機能の位置づけ

mmq を **base（レート制限付き Mistral chat / MCP server）として固定**したうえで、Web 検索やメタデータ補完をどこに置くかを整理する。

例として AbemaTV / Radiko を挙げるが、**他メディア・他サイトでも同じ型**（欠損メタの補完パイプライン）である。

---

## 1. 「検索」の4種（混ぜない）

| 記号 | 名前 | 実態 | 例 | 備考 |
|------|------|------|-----|------|
| **A** | 決定的取得 | 既知 URL / API / 番組表 | 公式エピソードページ、局の番組表 | 本線。安い・再現性高 |
| **B** | Web 検索 API | Brave / Tavily / Exa 等 | 「作品名 + 公式」で URL 発見 | 従量。クエリはコードが制御 |
| **C** | LLM 抽出 | 既に持ったテキスト → 構造化 | snippet/HTML から JSON | **mmq**（free-tier キュー） |
| **D** | LLM に検索させる | Mistral `web_search` コネクタ等 | モデルが自分で検索 | **採用しない**（コスト大） |

本線の順序:

```
A が主 → 足りなければ B → テキストが汚ければ C
```

**D は mmq base にも拡張本線にも載せない。**

議論では「検索」と言わず **A/B/C/D のどれか**を明示する。

---

## 2. コンポーネント責務

| コンポーネント | 持つ | 持たない |
|----------------|------|----------|
| **mmq (base)** | C 用 chat、共有キュー、MCP server（`ask_mistral` 等） | B/D、サイト固有スクレイパ、メディア固有ロジック |
| **search モジュール or 独立 MCP** | B（API キー、top-k、snippet 切り詰め） | Mistral レート実装 |
| **batch runner（α）** | ジョブ、キャッシュ、A→B→C の順序、リトライ、成果物 | キューの再発明 |
| **Vibe 等** | 手順の試作・ indvidual（β） | 本番バッチのオーケストレータ |

```
人 / 試作:  Vibe ──▶ search(B) + mmq(C)

本番バッチ:  batch runner
               ├─ A 決定的 fetch
               ├─ B search API（miss 時）
               └─ C mmq（抽出が必要な時だけ）
```

**原則: 検索 (B) は mmq の外。mmq は抽出 (C) の実行エンジン。**

---

## 3. 処理パターン

### α — バッチ本番（推奨本線）

```
キー（タイトル / ID / 放送日時 …）
  → [A] 公式・番組表・既知 URL
  → miss? → [B] search API（クエリはコードが決める）
  → [A'] ヒット URL を fetch
  → 構造化が必要? → [C] mmq「このテキストから JSON」
  → キャッシュ & 成果物（sidecar 等）
```

- オーケストレータ: **batch runner**（Vibe ではない）
- 検索の位置: **B は runner または search 専用モジュール**
- mmq: **C のときだけ**

Abema / Radiko に限らず、**「DL で取れないメタを Web で補う」系はすべて α**。

### β — Vibe で indvidual / 設計

```
人 + Vibe → search MCP (B) + mmq (C)
         → クエリ・スキーマ・公式 URL パターンを固める
         → α に落とす
```

本番の主経路にしない。

### γ — 1 ツール完結 UX（任意・後回し）

```
ask_mistral(..., use_web=true) → 内部で B→C
```

バッチ向きではない。やるなら拡張・デフォルト off。base には入れない。

### δ — Mistral connector (D)

**やらない。**

## 4. 意思決定ツリー

```
欠損メタを埋めたい
  │
  ├─ URL/API が分かっている？ ──yes──▶ [A] のみ。B しない
  │
  └─ no ─▶ 公式を「探す」必要がある？
              │
              ├─ yes ─▶ [B] → ページ fetch → 必要なら [C]
              │
              └─ no（本文は既にある）─▶ [C] のみ
```

ツリーが毎回変わるときだけ自律 agent。  
シリーズ固定・局固定なら **コードに書く（α）**。

---

## 5. mmq 拡張との優先順位

| 順 | 内容 | メモ |
|----|------|------|
| 0 | mmq base 固定 | 現行公開面。D を戻さない |
| **1** | **B: search API**（1 プロバイダから） | Brave / Tavily / Exa。mmq 外 |
| **2** | **バッチ α** | A→B→C、キャッシュ、スキーマ |
| 3 | β 用に search を MCP 化（任意） | Vibe から触りやすくする |
| 4 | mmq に MCP client / use_web（任意） | 「1 ツール完結」需要が出てから |

**「検索 API とバッチ α を作っていく」で正しい。**  
mmq に検索を内蔵することや、Vibe をバッチ本線にすることは必須ではない。

---

## 6. 命名（混線防止）

| 避ける | 使う |
|--------|------|
| 「検索を mmq に入れる」 | 「**発見 (B)** は runner / **抽出 (C)** は mmq」 |
| 「agent でやる」 | 「**自律 tool loop**」か「**固定パイプライン α**」か |
| 「Web 検索付き Mistral」 | 「**D（コネクタ）**」か「**B の後に C**」か |

README 上の mmq: **rate-limited Mistral chat (MCP/CLI)**。  
メタ補完パイプラインは **別ジョブ（α）**。

---

## 7. 実装前に決めると楽なこと

1. 1 件あたり **B 何回・C 何回**が上限か  
2. キャッシュキー（シリーズ ID、正規化タイトル、局+日時 等）  
3. 出力 JSON スキーマ（ドメインごと + 共通フィールド）  
4. search プロバイダの第一候補（まずは 1 社）

---

## 8. 一文

**発見 (B) と理解 (C) を分離する。**  
バッチでは runner が A→B を握り、必要なときだけ mmq に C を渡す。  
Vibe は α を発明する場所であり、毎晩回す場所ではない。
